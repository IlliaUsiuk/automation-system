# Бриф на застосунок "Портфель автоматизацій" (supplax.ai)

Статус: **не готові починати білд**. Два факти ще не перевірені (хостинг, БД).
Все інше нижче — вже прийняті рішення, готові до виконання, як тільки факти
підтвердяться. Це саме той "промпт на майбутнє", який просили: коли блокери
знімуться, просто виконати розділ "Готові команди для старту" по порядку.

## 1. Що це

Веб-версія портфеля автоматизацій — того самого, що mai в вигляді
ROI.md/COMPARISON.md/CONNECTIONS.md планувався як набір markdown-файлів
(скіл `automation-portfolio`, відкладений раніше). Тепер це реальний сайт на
`supplax.ai`, кілька людей з компанії заходять під логіном і бачать: список
автоматизацій, їх ROI, порівняння зі старим способом, зв'язки між ними.

## 2. Що вже вирішено

- **Backend: Flask** (не FastAPI, не Django). Причина: потрібні і HTML-сторінки,
  і JSON-ендпоінти (щоб автоматизації самі присилали статус/метрики), Flask
  робить обидва без зайвої церемонії, а для внутрішнього інструменту на кількох
  користувачів Django-адмінка й ORM-магія — зайва вага.
- **ORM: SQLAlchemy.** Не прив'язуємось до конкретної БД в коді — рядок
  підключення міняється, код моделей не міняється. Закриває питання 2.
- **БД для старту: SQLite.** Один файл, без окремого сервера БД, легко
  розгортати на VPS. Перехід на PostgreSQL — це заміна рядка підключення,
  якщо колись стане реальною проблемою одночасний запис від кількох людей
  (для "кількох людей з компанії" це малоймовірно найближчим часом).
- **Фронтенд: сервер-рендер, Jinja2-шаблони + звичайний CSS.** Без React/Vue,
  без збірки на Node. Якщо десь знадобиться інтерактивність без перезавантаження
  сторінки (фільтр списку, живий статус) — htmx, один script-тег, не окрема
  збірка.
- **Автентифікація: Flask-Login, акаунти створює адмін вручну** (немає
  самостійної реєстрації, немає email-верифікації, немає "забув пароль" на
  MVP-етапі — це реальна робота, яка не потрібна для кількох людей з довіреної
  команди). Паролі — хеш через `werkzeug.security`, не власний крипто.
- **Джерело правди: БД, не markdown-файли.** Дані живуть у SQLite/Postgres;
  якщо колись знадобиться git-історія змін ROI як у markdown-варіанті, це
  окрема команда "експортувати поточний стан у ROI.md" по кожній автоматизації,
  а не навпаки. Якщо це рішення виявиться неправильним (наприклад, хочеться
  саме git-diff на кожну зміну ROI) — сказати окремо, це змінює архітектуру.

## 3. Що ще треба перевірити, перш ніж рахувати деплой (блокери)

1. **Хостинг supplax.ai** — хто зареєстрував домен і що вже є:
   - Чи є VPS (Hetzner/DigitalOcean/інше) з SSH-доступом? Потрібен root/sudo.
   - Якщо VPS немає — домен просто зареєстрований, сервера нема взагалі?
   - Хто керує DNS-записами домену (потрібно буде додати A-запис на IP сервера
     або створити піддомен, наприклад `portfolio.supplax.ai`)?
2. **Скільки людей і які в них ролі** — просто "логін для кількох людей" уже
   є, але чи всі мають однакові права, чи потрібен окремий рівень "адмін
   додає автоматизацію" проти "тільки перегляд"?

Без пункту 1 неможливо написати конкретні команди деплою (Gunicorn/nginx/
systemd — це для VPS; для чогось типу Render/Railway/Fly.io — зовсім інший
процес). Як тільки є відповідь — деплой-частина нижче стає виконуваною.

## 4. Модель даних (чернетка)

```
User            id, email, password_hash, role (admin | viewer)
Automation      id, slug, name, one_liner, status (live|prototype|deprecated),
                owner, created_at
ROIEntry        automation_id, hypothesis, metric_description,
                confidence (estimated|measured), measured_value, measured_at,
                qualitative_notes
Comparison      automation_id, old_way_description, limitations
FeatureRow      comparison_id, feature, old_way, new_way, why_it_matters
Connection      automation_id, connected_automation_id,
                relationship_type, shared_resource
ReviewLogEntry  automation_id, round_label, found, changed, rejected
                (це і є "backlog" з automation-portfolio, тепер у БД)
```

## 5. MVP-функції, у порядку

1. Логін (Flask-Login), адмін створює перших користувачів вручну (CLI-команда,
   не UI-форма — на старті це безпечніше й швидше).
2. Список автоматизацій (`/automations`) — таблиця: назва, статус, коротке ROI.
3. Сторінка однієї автоматизації — повний ROI, порівняння, зв'язки з іншими.
4. Форма додавання/редагування автоматизації (тільки роль admin).
5. Сторінка зв'язків — граф чи хоча б таблиця "хто з ким пов'язаний".
6. JSON-ендпоінт `POST /api/automations/<slug>/status` — щоб сама автоматизація
   (n8n-воркфлоу, скрипт) могла присилати свій статус/метрику без людини.

Усе, що складніше (дашборди з графіками, експорт у markdown, повноцінні ролі) —
після MVP, не зараз.

## 6. Деплой — план під VPS (виконати, коли відомий пункт 3.1)

1. VPS: Ubuntu LTS, створити non-root користувача, `ufw` тільки 22/80/443.
2. Встановити Python 3.12, `pipx`/`venv`, застосунок у `/opt/portfolio/`.
3. Gunicorn як WSGI-сервер застосунку (не `flask run` — той для розробки).
4. systemd unit-файл — рестарт при падінні, старт при перезавантаженні сервера.
5. nginx як reverse proxy перед Gunicorn, статика (`/static/`) віддає сам nginx.
6. DNS: A-запис `portfolio.supplax.ai` (або обраний піддомен) → IP сервера.
7. TLS: certbot (Let's Encrypt), автопродовження сертифіката.
8. Бекапи: щоденний cron, що копіює файл SQLite в окреме місце (S3/інший сервер) —
   для файлової БД це реально просто, не пропускати.

Якщо замість VPS буде PaaS (Render/Railway/Fly.io) — пункти 1-5 замінюються на
конфіг-файл платформи, решта (DNS, TLS) вона зазвичай бере на себе.

## 7. Готові команди для старту (коли блокери з розділу 3 закриті)

Дати мені по черзі:

1. "Хостинг: VPS з SSH, ось дані для підключення (або: PaaS, ось який)."
2. "Створи Flask-застосунок за брифом APP-BUILD-BRIEF.md: моделі з розділу 4,
   логін, MVP-функції з розділу 5."
3. "Задеплой за розділом 6 (або під обрану PaaS)."

Після кроку 1 я одразу переписую розділ 6 під реальні дані замість плану "на
два сценарії" — і можна білдити.
